## Question 12

```text
Round: First implementation milestone
Question: How composable should the JSON authoring path be in this first milestone?
Description (Markdown source):
A flat form schema is quick to demonstrate, but it would only exercise built-in fields. A small component tree can support nested groups and rows, with skill-supplied local JavaScript rendering custom component types.

For example, a skill could put a custom preview beside a slider without changing Go. This does not require a new expression language, package registry, or universal workflow format. Plain HTML remains available either way.
Recommendation: Prove a small component tree and one skill-defined component early. Extensibility is central to Fungi, so the first milestone should exercise it directly.
Options: Nested composition plus local custom components / Flat built-in fields first; composition and custom JSON components follow
Selected: Flat built-in fields first; composition and custom JSON components follow
Notes: keep this simple first for now, i have bigger ideas for JSON authoring.
```

## Question 13

```text
Round: First implementation milestone
Question: What should closing the native window mean?
Description (Markdown source):
Closing must never be mistaken for submitting. In both choices, retain the latest saved draft and allow an explicit reopen. Custom pages can only recover draft data they have saved.

Returning a “closed” outcome lets the agent know this interaction ended without an answer. Treating close as a pause leaves the interaction awaiting a later reopen, submission or cancellation, without waking the agent merely because the window closed.
Recommendation: Return a distinct “closed” outcome and preserve the saved draft. It makes the lifecycle explicit and avoids an invisible pending interaction.
Options: End this interaction with a closed outcome; preserve its draft / Pause without notifying the agent; await reopen, submit or cancel
Selected: End this interaction with a closed outcome; preserve its draft
Notes:
```

## Question 14

```text
Round: First implementation milestone
Question: Should the first milestone exercise a native helper process as an extension?
Description (Markdown source):
Native helper executables are already allowed by the architecture. This choice is about when to prove that boundary.

A tiny bundled helper could accept JSON and return JSON plus an artifact through the same session/result path. It would test the contract independently of Electron, without requiring a full screenshot app or a native widget library. HTML/JSON authors would not need to use this advanced interface.
Recommendation: Include one tiny helper to prove the engine can support a capability outside Electron. Keep a production screenshot/capture UI for a later workflow.
Options: Include a tiny native helper contract test / Prove HTML/JSON first; native helper support follows
Selected: Include a tiny native helper contract test
Notes:
```

## Question 15

```text
Round: First implementation milestone
Question: Does the first milestone need live updates from another local process after a window opens?
Description (Markdown source):
With either choice, sliders, animations, drawings and validation can react immediately inside the UI while the model is idle.

This question concerns external updates: for example, a development tool sending new preview data into the already-open Fungi window. Supporting that now adds an ongoing update interface beyond launch input and final submission. It does not require model polling, but it expands the first contract.
Recommendation: Start with launch input, local UI interaction and final submission. Add external live updates once a concrete workflow needs them.
Options: Launch input and local interaction are enough initially / Include updates from other local processes immediately
Selected: Launch input and local interaction are enough initially
```
