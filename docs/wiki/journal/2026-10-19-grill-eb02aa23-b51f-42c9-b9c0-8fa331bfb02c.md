## Question 1

```text
Round: Fungi: foundation decisions
Question: What should “single binary” mean when a skill adds new capabilities?
Description (Markdown source):
The core can be one executable per OS/architecture. A skill's HTML, CSS, JavaScript, and images are content files. New native functionality must either live in an additional executable, be compiled into fungi, or be bundled and extracted.

This choice determines how easily someone can publish a new capability without rebuilding fungi.
Recommendation: One fungi executable plus ordinary skill assets, with optional native helper executables for capabilities that need them. Basic UI authors only write HTML and call the bridge.
Options: One core executable; skill assets and optional native helpers / Every workflow must use one executable; rebuild fungi for new native capabilities / One download may extract bundled native helpers at runtime
Selected: One core executable; skill assets and optional native helpers
Notes: one core fungi executable "orchestrates" the workflow. skills may bring in optional excutables or assets. fungi itselt may also be optionally be extended with capabilities stored in a relatively-adjacent folder.
```

## Question 2

```text
Round: Fungi: foundation decisions
Question: What deployment tradeoff is acceptable for the first native webview renderer?
Description (Markdown source):
System webviews keep the renderer small. macOS has WebKit; Windows needs WebView2; Linux needs compatible GTK/WebKitGTK libraries. Shipping a full rendering engine changes size and maintenance substantially.

Sources: [webview requirements](https://github.com/webview/webview#prerequisites), [WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).
Recommendation: Use system webviews on an explicit supported desktop baseline and report missing support clearly. Keep automatic installation out of the first release.
Options: System webviews on supported desktops; clearly reject missing support / System webviews with an automatic browser fallback / Bundle a rendering engine to avoid external webview prerequisites
Selected: Bundle a rendering engine to avoid external webview prerequisites
Notes: bundle the simplest and lightest rendering engine you can find. i don't want to run into webview2, webkitgtk issues on different machines. i want it to run cleanly straight out the box.
```

## Question 3

````text
Round: Fungi: foundation decisions
Question: Which authoring interface should we make easiest first?
Description (Markdown source):
A direct path lets a skill supply an HTML file or asset folder and call a tiny bridge such as ready(), submit(), and cancel(). Existing libraries remain usable. A catalog path lets an agent generate JSON from a predefined set of components, but someone must maintain the catalog and renderer mapping.

```mermaid
flowchart LR
  Skill[Skill and UI files] --> Engine[Fungi session]
  Engine --> UI[Renderer]
  UI --> Result[Saved response]
  Result --> Agent[Calling agent]
```
Recommendation: Ordinary HTML/assets with a tiny bridge. Include a small primitive test UI; add JSON-driven forms or other component catalogs above that interface when useful.
Options: HTML/assets plus a tiny bridge first / JSON component catalog first, with HTML as an escape hatch / Both paths equally supported in the first release
Selected: Both paths equally supported in the first release
````

## Question 4

```text
Round: Fungi: foundation decisions
Question: If fungi cannot establish automatic delivery to the current agent, what should launch do?
Description (Markdown source):
A background process ID is not enough to wake an idle agent. Harnesses expose different completion and callback capabilities. Repeated model polling remains prohibited in every option.
Recommendation: Stop before opening and explain the unavailable delivery route. Offer a separately selected manual mode so automatic-return guarantees are never implied when they are absent.
Options: Stop before opening; allow explicitly selected manual mode / Open the UI and ask the user to send “done” after submitting
Selected: Open the UI and ask the user to send “done” after submitting
Notes: best effort automatic delivery on every popular harness. fallback to saying "done".
```

## Question 5

```text
Round: Fungi: foundation decisions
Question: Which agent location must the first release support?
Description (Markdown source):
A local executable can open a window on the same desktop. An agent running on a remote server or in a container needs an explicit connection to the user's desktop and a way to transfer artifacts. That adds connection setup and authentication beyond the local runner.
Recommendation: Start with agents and UI on the same desktop. Keep the protocol compatible with a future remote transport without building that transport now.
Options: Local agents and UI on the same desktop first / Remote/container agents must reach the user's desktop in the first release
Selected: Local agents and UI on the same desktop first
Notes:
```

## Question 6

```text
Round: Fungi: foundation decisions
Question: What recovery should be automatic after the relevant processes have exited?
Description (Markdown source):
Hours of AFK time and ordinary sleep can leave the local session alive without model polling. Once all fungi and harness processes have stopped, delivery needs something to start them again. Saved results can survive independently.

This choice concerns automatic restart, not whether responses are saved reliably.
Recommendation: Preserve drafts/results and support explicit reopen or collect after restart. Prove reliable live-session AFK behavior first; add harness-start hooks or login services only if needed.
Options: Explicit reopen/collect after restart is acceptable / Recover automatically when the harness next starts / Recover and deliver automatically after login/reboot
Selected: Explicit reopen/collect after restart is acceptable
Notes: even though i wanted automatic delivery, on certain extreme cases where it proves difficult, we may fallback to the user manually saying "done"
```
